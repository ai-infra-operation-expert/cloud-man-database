## 0. 核心理念

> **AI Native 团队 = 把全团队所有 work(研发/工单/值班/PDSA/集测/PD/PM)都当成 project,全部数字化,入 context graph,然后让 AI + 人协作,飞轮越转越快。**
>
> **Process 是 context 的输入管道,People 是飞轮的驱动力,Measure 是飞轮的转速表,Context 是飞轮的本体。**

### 关键转换

| 维度 | 传统 | AI Native |
|---|---|---|
| 知识载体 | 文档/wiki(死的) | Context graph(活的、关联) |
| 决策模式 | 经验 + 流程 | Context + AI 推理 + 人工 review |
| 工单处理 | 人查 SOP → 处理 → 关闭 | AI 初判 → 人 review → AI 沉淀 |
| 度量 | 工单数、关闭率 | MTTR、FCR、知识复用率 |
| 工程师价值 | 修问题 | 设计 context 流动 + 监督 AI |

> **目标:让 AI 成为第 N+1 个 SRE,工单流程里永远有 AI 在跑。**

## 2. Context 维度

### 2.1 为什么 Context 是 AI Native 团队的核心资产

**反直觉的事实**:
- 传统团队 = 人是核心资产(离职 = 知识流失)
- AI Native 团队 = **context 是核心资产**(人离职,context 沉淀,新人 + AI 立刻能用)

**当前 context 状态**:
- 工单在工单系统(有)
- 复盘在 Confluence/钉钉(有,但散)
- 跑路经验在老员工脑子里(在,但走人就没了)
- runbook 在 wiki(有,但常过期)
- 客户背景在 CRM(有,但和故障记录不联通)

**这就是"金矿"在脚下但挖不出来**。

### 2.2 Context 4 属性

| 属性 | 含义 | 反例 |
|---|---|---|
| **可检索** | AI 能找到 | Word 文档深处、邮件附件 |
| **可关联** | 跨工单/跨客户/跨组件 | 一个工单一个文件夹,无 link |
| **可演化** | 每次新工单更新现有 context | 文档写完就锁死 |
| **可验证** | 知道这 context 是对的/错的 | 没人 review,老 context 一路错到底 |

### 2.3 Context 资产地图

```
                    ┌─ 客户环境(集群拓扑/版本/网络)
                    │
                    ├─ 故障历史(每工单的根因 + 方案)
                    │
   知识资产 ─────── ├─ 复盘(每次 P0/P1 的复盘文档)
                    │
                    ├─ 决策日志(架构/SOP 变更的 why)
                    │
                    ├─ Runbook(操作步骤)
                    │
                    └─ 客户画像(SLA/合规/沟通偏好)
                    │
                    ┌─ 监控数据(Grafana / ARMS)
                    │
   实时数据 ─────── ├─ 工单系统(现在/历史)
                    │
                    └─ Slack/钉钉(沟通历史)
```

### 2.4 Context 飞轮

```
       ┌─→ 客户报错进来
       │
       ↓
    AI 查 context
       │
       ↓
    给出诊断草稿
       │
       ↓
    工程师处理(并 review AI 输出)
       │
       ↓
    AI 把新 case 写回 context
       │
       ↓
    下次类似问题 → 更准的草稿
       │
       └─→ (回到开始)
```

### 2.5 Context 建设 3 阶段

**阶段 1(0-3 月):Context 资产化** — 先有再好用
**阶段 2(3-6 月):Context 关联化** — 相似工单检索,最高 ROI
**阶段 3(6-12 月):Context 智能化** — AI 主动推送,主动发现缺口

## 3. Process 维度(核心修订)

### 3.1 核心理念:Everyone's work = a project = context

**Process 不是"工单/SOP/复盘流程",而是"把团队所有人所有角色的 work,都当成一个 project 数字化,然后入 context"。**

### 3.2 6 大 Work Stream 数字化清单

#### Work Stream 1:研发 Work
**当前痛点**:
- 设计讨论在飞书/钉钉,合完就散
- Code review 评论在 PR 里,合入后查不到
- 部署决策在群里"拍脑袋"
- 故障复盘和代码 commit 关联不上

**数字化项目卡 schema**:
```yaml
项目卡:
  需求: <一段话 from PM>
  设计: <架构图 + 决策理由(ADR 链接)>
  PR: #1234(关联 commit/合入)
  部署: <环境/版本/回滚方案>
  验证: <验证清单 + 截图/监控链接>
  关联: <相似项目/相关故障>
  经验: <复盘链接>
```

#### Work Stream 2:工单 Work
**数字化强化**:
- 强制 3 个必填字段:**根因 + 方案 + 经验教训**
- IM 沟通同步归档到工单(webhook / 机器人)
- AI 自动从工单正文**预填**这 3 个字段(工程师 review)

#### Work Stream 3:值班长 Work
**值班卡 schema**:
```yaml
值班卡:
  日期/值班人: 
  告警清单: <每条告警 → 响应 → 处理 → 关闭>
  升级记录: <谁/何时/为什么升级>
  关键决策: <值班时做的决策 + 理由>
  交接事项: <下一班要注意什么>
  关联: <触发的故障卡/工单>
```

#### Work Stream 4:PDSA Work(质量改进)
**PDSA 卡 schema**:
```yaml
PDSA 卡:
  P(Plan):  <改什么/为什么/假设>
  D(Do):    <具体动作/时间/人>
  S(Study): <数据/对比/偏差分析>
  A(Act):   <结论/推广/再迭代>
  关联: <触发的项目/工单/故障>
```

#### Work Stream 5:集测 Work
**测试卡 schema**:
```yaml
测试卡:
  计划: <范围/策略/准入准出>
  用例: <覆盖点 + 自动化率>
  执行: <通过率/阻塞/缺陷>
  报告: <结论 + 风险评估>
  关联: <对应项目/需求>
```

#### Work Stream 6:PD/PM Work
**决策卡(ADR)schema**:
```yaml
决策卡(ADR):
  背景: <为什么需要决策>
  备选: <A / B / C 方案对比>
  决策: <选了谁 + 理由 + 反对意见>
  后果: <实施后效果 + 复盘>
  关联: <相关项目/工单/客户反馈>
```

### 3.3 数字化 3 层次

#### 层次 1:结构化(0-2 月)
- 目标:把人脑/IM/邮件里的 work,搬到结构化字段
- 做法:选 1-2 个工具(飞书多维表 / Jira),强制每种 work 填结构化字段
- 完成标志:80% 的 work 有结构化记录

#### 层次 2:关联化(2-6 月)
- 目标:work 之间建立 link
- 做法:每个卡可以 link 到其他卡
- 完成标志:任何 work 都能反向追溯到 3 层以上的 context

#### 层次 3:智能化(6-12 月)
- 目标:AI 主动推送、主动发现缺口
- 完成标志:团队感觉"AI 是个靠谱的助理,主动帮忙而不是被动查"

### 3.4 接入 Context Graph 的标准格式

所有 work 数字化后,统一抽象成 7 字段:

```yaml
work_card:
  who:        # 谁做(角色 + 人)
  what:       # 做什么(项目/工单/PDSA/ADR/...)
  when:       # 何时(开始/结束/关键节点)
  why:        # 为什么(目标/假设/上下文)
  result:     # 结果(成功/失败/学到什么)
  links:      # 关联(其他 work 卡的 link)
  context:    # 关联的 context(组件/客户/ADR/复盘)
```

**这就是 context graph 的"节点 schema"**。

### 3.5 工具栈建议

**P0(立刻做,投入小)**:
1. **工单 → 结构化 context 提取器** — LLM + prompt
2. **相似工单检索器** — 向量化 + 语义搜索
3. **SOP/RUNBOOK 数字化** — 飞书/钉钉文档 → 向量化 + tag 化

**P1(3 个月内)**:
4. **客户环境 registry** — ACK/AI Stack 客户环境元数据
5. **故障图谱(Knowledge Graph)** — Neo4j / 阿里云 GDB
6. **AI 工单 copilot** — 基于上面所有 context 训练的 agent

**P2(半年到一年)**:
7. **决策日志系统(ADR + 复盘)** — 结构化 ADR 模板
8. **AI 监督的复盘自动化** — 从 P0/P1 事故自动生成 PM 草稿

## 4. People 维度

### 4.1 角色变化(12 个月后)

| 角色 | 旧 | 新 | 关键能力 |
|---|---|---|---|
| 资深 SRE / 研发 | 50% | 25% | 架构 + 复杂故障 + 跨团队 |
| 普通 SRE / 研发 | 50% | 25% | review AI + 监督 + 沟通 |
| **Context 工程师** 🆕 | 0% | **15%** | 知识图谱 + context 治理 + AI 训练数据 |
| **Work 数字化工程师** 🆕 | 0% | **20%** | 把各角色 work 数字化入 context |
| **AI Trainer** 🆕 | 0% | **10%** | 微调 copilot + 评估 AI 输出 |
| **平台架构师** 🆕 | 0% | **5%** | AI 工具链整合 |

### 4.2 关键新角色:Work 数字化工程师

**他们不修 bug、不写代码**,专门负责:
- 和每个角色深度合作,**把 work 重新设计成"可数字化"的形式**
- 设计每种 work 的卡 schema
- 推动"结构化填写"的纪律
- 训练团队:写得好、写得全、写得有 context
- 和 Context 工程师协作,入 context graph

**典型画像**:
- 有 SRE/研发/PM 背景(懂业务)
- 有产品经理的"抽象 + 落地"能力
- 不怕推流程、能跟人打交道
- 懂一点点 AI 更好(知道 AI 想要什么数据)

### 4.3 文化建设

**AI Native 文化 4 句真言**:
- ✅ **"写下来 > 记在脑子里"** —— 不写的人拖团队后腿
- ✅ **"被 AI 引用是种荣誉"** —— 谁写的 context 被 AI 用得最多,谁最被认可
- ✅ **"AI 出错是常态,review AI 是基本功"** —— 不期望 AI 100% 对
- ❌ ~~"我经验最丰富,我说了算"~~ —— AI + context 可能比老员工更准

**负责人文化建设的具体动作**:
1. 自己带头用 AI(自己写 5 个 skill,示范给团队)
2. 公开 review AI 的输出(让团队看到"review AI 是日常工作,不是额外负担")
3. 失败 case 公开复盘(AI 错的时候,团队一起学)
4. 内部讲师制(团队成员轮着讲"我最近用 AI 干成了啥")

### 4.4 招聘变化

**旧 JD**:

**新 JD**:

## 5. Measure 维度

### 5.1 旧 KPI(应废掉或降权)

| 旧 KPI | 为什么不能要 |
|---|---|
| 工单数量 | 越多越好还是越少越好?AI 时代已无意义 |
| 工单关闭率 | 关得快 ≠ 关得好 |
| 客户满意度(单次) | 一次满意不算,长期信任才算 |

### 5.2 新 KPI(AI Native 团队核心)

| 类别 | KPI | 含义 | 计算方式 |
|---|---|---|---|
| **效率** | MTTR | 平均恢复时间 | 工单/故障处理时长 |
| **效率** | FCR-AI | AI 草稿一次采纳率 | review 记录中"采纳 / 修改采纳 / 重写" |
| **效率** | 新人 AI 化上手周期 | 入职到能独立 review AI 输出 | 30 / 60 / 90 天 |
| **Context** | Context 完整度 | work 卡的必填字段填充率 | 字段填充比例 |
| **Context** | Context 关联密度 | 每个 work 平均 link 数 | 平均 link 数 |
| **Process** | Work 数字化覆盖率 | 各角色 work 入卡比例 | 各角色 work 卡数 / 总 work 数 |
| **Process** | AI 主动推送命中率 | AI 推送被采纳的比例 | 推送采纳 / 推送总数 |
| **People** | Context 贡献排行 | 谁写的 context 被引用最多 | 引用计数 |
| **组织** | AI 接管率(L1) | L1 work AI 自主处理比例 | L1 总量中 AI 自主处理 |

### 5.3 激励变化

- **个人考核**:不再只考"你修了几个工单",加"你贡献了多少 work 卡和 context"
- **团队考核**:加"work 数字化覆盖率""AI 接管率""context 关联密度"
- **新角色专项**:Work 数字化工程师 / Context 工程师 的核心 KPI 是"团队 work 数字化覆盖率"

## 7. Anti-patterns(避坑)

### ❌ Anti-pattern 1:"Process 数字化 = 写更多文档"
- **问题**:写文档是手段,入 context 才是目的
- **正解**:**结构化字段 + AI 预填 + 强制 link**,不是 Word/PDF

### ❌ Anti-pattern 2:"先建平台再数字化"
- **问题**:大平台是空架子
- **正解**:**从一个 work stream(工单)切入**,schema 跑通,再扩

### ❌ Anti-pattern 3:"让工程师自己数字化"
- **问题**:工程师最讨厌填表
- **正解**:**AI 预填 80% + 工程师 review 20%**

### ❌ Anti-pattern 4:"Context 是 IT 项目,招个工程师搞定"
- **问题**:context 治理是**业务变革**,不是 IT 项目
- **正解**:**每个角色都参与**。负责人亲自推,Work 数字化工程师设计 schema,各角色 owner 落地

### ❌ Anti-pattern 5:"AI 替代人,人减少"
- **问题**:AI 替代机械部分,人转型为判断/设计/沟通
- **正解**:**总人数不变或增加**,但结构变

### ❌ Anti-pattern 6:"找个大模型就行"
- **问题**:大模型是底座,不是解决方案
- **正解**:大模型 + 你的私有 context,才有壁垒
